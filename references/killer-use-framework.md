# Killer-use framework

Summarized in our own words from Andres Fortino, "Killer Uses Accelerate the Diffusion of Innovation" (2012, 2016), which builds on Everett Rogers, *Diffusion of Innovations*.

## Core ideas

- **Killer app:** an application so popular that it pulls a whole platform into wide use. The standard example is the early spreadsheet (VisiCalc, then Lotus 1-2-3), which drove business adoption of the personal computer.
- **Killer use:** the unmet need behind a killer app. It is fundamental and compelling, and it was often not recognized before the application met it. For the spreadsheet, it was on-the-fly "what if" financial analysis.
- **Why it matters:** once a killer use is met, people adopt the tool on their own and spread it to others. Adoption becomes viral, so the organization does not need to mandate the tool or run heavy training, because users are motivated to learn it.
- **Two ways to use the idea:** design a new application around a known killer use, or find a killer use for an application that already exists and use it to drive adoption.
- **It may not be the intended use.** The killer use of an application is sometimes different from what it was built for.
- **Supporting levers** (from Rogers): opinion leaders, change agents, technical experts and lead users can start the spread. A killer use gives them something worth spreading.

Fortino's example: for a company adopting social networking tools, the proposed killer uses were an internal skills and work-history directory for staffing projects, a searchable wiki of expert solutions, and shared workspaces for problem solving with outside experts.

## Scoring criteria

Score each use case 1 (low) to 3 (high) on each criterion. Maximum total is 15.

| Criterion | Question | 1 | 3 |
| --- | --- | --- | --- |
| Compelling | How much does the unmet need cost the user today? | Mild inconvenience | Lost jobs, money, grades or hours every week |
| Unrecognized | Do users see the need before the tool shows it to them, and do existing tools already meet it? | Obvious and already met by generic tools | Users do not name it, and nothing meets it well |
| Frequency | How often does the need come up? | A few times a year | Weekly or more |
| Spread | Is the result visible enough that users show or tell peers? | Private, invisible result | Result people share or compare |
| Low effort | How little setup or training is needed to get value? | Hours of setup or training | Value within the first session |

The use case with the highest total is the candidate killer use. Break ties on Unrecognized, then Spread, since those two are what separate a killer use from an ordinary one.

## Hook versus killer use

A use case can score well because it is easy and frequent (a good **hook** that gets people to try the tool) without being the need that makes them keep using it and pass it on (the **killer use**). Name both when they differ.
